# 07 · 预处理管线（面对"没见过"的素材）

> 你给的 19 个会员只是样例，真实批次还会出现 HEIC 实况、竖拍横转、斜拍报告、截图、多人合影、糊片、新门店的不同拍摄习惯。
> 所以预处理不是"按样例写死"，而是**归一化管线 + 分类感知的矫正 + 强制去重 + 可人工覆盖的质量闸门 + 开放集兜底**。

## 1. 为什么必须有独立一层

| 真实存在的情况 | 直接进识别会怎样 |
| --- | --- |
| iPhone 默认 **HEIC/HEIF** + 实况照片（HEIC + 同名 MOV） | 读不出图 / 实况被拆成两条素材 |
| 手机竖拍但 EXIF 缺失 | 图是躺着的，体测图被判"横版不合格" |
| 体测报告**斜着翻拍**（样例 `杜明钢` 那张） | OCR 读错行、数字错位 |
| 截图（微信/抖音）混进生活照 | 被当成生活照，裁切后一片黑边 |
| 同一张图被压过 3 次、尺寸不同 | 重复占额度，甚至前后判错 |
| 4 亿像素全景 / CMYK TIFF / PNG 带 alpha | 内存爆 / 颜色错 |
| 文件名 GBK、`__MACOSX`、`._xxx`、`Thumbs.db` | 解包乱码、垃圾文件污染分类 |

## 2. 入库流程（对应总流程第 1–6 步）

```
zip ─①安全解包─②资产登记─③格式归一─④质量评分─⑤强制去重─⑥工作副本
                                                          │
                                              ⑦分类/结构化（VLM，总流程第 6 步）
                                                          │
                                              ⑧文档矫正（仅报告类，总流程第 7 步）
                                                          │
                                              ⑨统一命名 + asset.json
```

> 之所以把"矫正"放在分类之后：**矫正策略依赖类别**（只对报告类矫正，生活照/训练照不许动），见 §④ 的说明。

### ① 安全解包
- 支持 zip / tar.gz / 7z（`.rar` 明确提示转换）。
- 拒绝：路径穿越、符号链接、设备文件、加密包、zip bomb（解压后 >8 GB 或压缩比 >200:1）、条目数 >20000。
- 跳过：`__MACOSX/`、`._*`、`.DS_Store`、`Thumbs.db`、`desktop.ini`（本次上传的 demo 包里就有这些）。
- 文件名编码：UTF-8 标记优先，否则按 GBK/Big5 回退。
- 嵌套 zip 最多解 2 层，记录来源链。

### ② 资产登记（看字节，不看扩展名）
- MIME 嗅探（magic bytes）+ 扩展名交叉校验，不一致以字节为准并告警（`.jpg` 实为 HEIC 很常见）。
- 记录 `sha256`、字节、像素、色彩模式、EXIF（时间/设备/方向/GPS）、时长/音轨。
- 判定 `live_photo`：同名 `.HEIC` + `.MOV` → 合成一条素材（取图，视频留档）。
- **MP4 暂不处理**（本期）：只登记元数据，标 `video_deferred`，不抽帧、不影响成品判定（见 06-D10）。

### ③ 格式归一
| 输入 | 处理 |
| --- | --- |
| HEIC / HEIF | `pillow-heif` 解码 → JPEG(q95)，保留原件 |
| RAW（CR2/NEF/ARW） | `rawpy` → JPEG；失败进隔离舱 |
| TIFF / CMYK / 16bit | 转 sRGB 8bit JPEG |
| PNG / WebP / GIF | 首帧 → JPEG，alpha 另存 PNG |
| BMP | 转 JPEG |
| PDF | 有文本层→直接解析；无文本层→200 DPI 渲染页图 |
| DOCX | `python-docx` 取文本+表格，另存 PDF 供 O14 渲染 |
| MP4 / MOV | **本期不处理**：登记 + 标 `video_deferred` |
| 其他（psd/ai/sketch） | 登记后进隔离舱 |

### ④ 分类感知矫正（**执行时机在分类之后**；关键：只矫正该矫正的）

**矫正策略按素材类别走，不是一律拉直**：

| 类别 | 方向(EXIF/旋转) | 透视/弯曲矫正 | 理由 |
| --- | --- | --- | --- |
| 体测报告 `R1/R2` | ✅ | ✅ **必须** | 翻拍必然有透视，不矫正读不准数字 |
| 训练报告/文档 `T`（PDF/翻拍） | ✅ | ✅ 翻拍时矫正 | 同上 |
| 体测图 `F/S/B` | ✅ | ❌ 不做 | 靠墙面网格本就是竖直拍摄，拉直反而破坏比对 |
| 生活照 `L` | ✅ | ❌ 不做 | **可能是故意斜拍/构图**，不许"纠正"用户的审美 |
| 训练日常图 `D` | ✅ | ❌ 不做 | 抓拍动态，矫正会切掉人物 |
| 会员感言截图 `Q` | ✅ | ❌ 不做 | 截图本身是正的 |

> 一句话：**只对"文档类"做几何矫正；人像类只纠正方向，不动透视。** 这条写死在规则里，避免把艺术照拉成证件照。

#### 矫正流水线（文档类）

```
① 文档检测：找纸张四边形/掩膜
      ├─ 成功 → 单应变换（确定性、<50ms）
      └─ 失败/多张纸/背景杂乱 → 进模型路径
② 模型去弯曲（SOTA，见下表）：处理纸张弯曲、镜头畸变、阴影
③ 质量复核：
   - OCR 文本行直线度 + 识别置信度 是否提升
   - 边缘是否拉歪（面积/长宽比异常）
   - 提升不足或结果异常 → 回退"只用单应"或"用原图"
④ 兜底：全部失败 → 保留原图 + VLM 直接读数，标 warp_failed
```

#### 候选模型（2024–2026 SOTA，均为开源）

| 模型 | 年份/出处 | 特点 | 工程成本 | 我们的用法 |
| --- | --- | --- | --- | --- |
| **UVDoc** | 2023 / TUM，已并入 🤗 Transformers | 无监督文档去弯曲，权重在 HF，`pip install transformers` 即用 | **低** | **默认模型**（弯曲/手持拍摄） |
| **DocRes** | CVPR 2024，[官方仓库](https://github.com/ZZZHANG-jx/DocRes) | 统一复原：去弯曲 + 去阴影 + 外观增强 + 去模糊，手机实拍效果好 | 中（需按仓库装依赖） | 阴影/褶皱严重时的第二选择 |
| **DocScanner** | IJCV 2025 | 渐进式矫正，几何鲁棒 | 中 | 备选，参与 bake-off |
| **ForCenNet** | ICCV 2025 | 前景中心化矫正，最新 SOTA（论文阶段） | 高（工程化未验证） | 观察，暂不上线 |
| 传统单应 | OpenCV | 零依赖、确定性、可解释 | 极低 | **首选**（平整纸张直接用） |

依赖与体积：UVDoc 权重约 100–200 MB，CPU 也可跑（单张 ~1–2 s），GPU <0.3 s；不与现有 SAM2 抢显存（串行调用同一把 GPU 锁）。

**选择逻辑**（先便宜后贵）：

```
平整纸张（四角检出 + 边线直）→ 单应，结束
弯曲/阴影/四角失败 → UVDoc
UVDoc 后 OCR 提升 < 阈值 → DocRes 再试一次
仍不行 → 原图 + warp_failed 标记（VLM 读数兜底）
```

**验证方法**：拿 demo 里全部报告类照片（参考模板 2 张 `体测报告-初始/阶段性` + 各店识别出的翻拍照）做 bake-off，指标 = 数字字段 OCR 准确率 + 文本行直线度 + 人工目检；准确率提升 <5% 就不引入模型，保持传统方案。

### ⑤ 质量评分（默认丢弃，但可人工覆盖）

| 指标 | 阈值（可配） | 判定 |
| --- | --- | --- |
| 清晰度（Laplacian 方差，归一化） | < 0.35 | `blurry` |
| 曝光（过曝/欠曝像素占比） | > 35% | `bad_exposure` |
| 人物占比（YOLO 人体框/全图） | < 3% | `subject_too_small` |
| 分辨率（短边） | < 800 | `low_res` |
| 截图特征（状态栏/输入框/纯色边） | 命中 | `screenshot` |
| 人脸可检（仅体测/生活照） | 连续两次失败 | `face_missing` |

**处置规则（按你的要求改成硬丢弃 + 可覆盖）**：

```
评分不达标 → 该素材默认丢弃（status=dropped）
           → 记录 drop_reason（可读中文 + 机器码 + 指标值）
           → 出现在"素材体检"里，标注会影响哪几张成品
           → 提供两个动作：
              ① 强制使用：status=forced，照常用，成品加"人工放行"标记
              ② 更换素材：上传一张新图 → 重新评分 → 通过则替换，不通过则给出原因
```

- 丢弃**不等于删除**：原文件保留在 `_dropped/`，随时可强制使用。
- 强制使用会在 `manifest` 和成品角标记 `forced_by_human`（谁、何时、原因为空时必填）。
- 更换素材走同一套评分与分类，避免"上传一张更差的图绕过闸门"。

### ⑥ 去重（强制执行）

- `sha256` 精确去重：同文件多处出现只算一次（demo 包里 `(1)` 后缀的重复就有不少）。
- `pHash` 近似去重（汉明距离 ≤6）：同图不同尺寸/压缩合并，保留最清晰、分辨率最高的一张，其余 `duplicate_of`。
- **前后两张 pHash 相同**（其实是同一张）→ 判定"没有对照"，不出 VS 版，记 `same_image`。
- 跨会员去重：不同会员之间出现同一张图（教练传错）→ 标记 `shared_across_members`，进复核。
- 去重在分类**之前**执行，省掉重复的 API 调用。

### ⑦ 工作副本
- 原图只读；`work/` 下生成三档：`thumb` 256（分类）、`work` 2048（检测/分割/OCR）、`full` 原分辨率（渲染）。

## 3. 开放集：遇到没见过的素材

```
第 1 层  按已知 6 类 + 子属性分类（VLM few-shot）
第 2 层  置信度不足或 unknown → 不做任何自动决策
第 3 层  进隔离舱 _quarantine/（缩略图 + 原因 + 模型猜测）
第 4 层  人工标注一次 → 沉淀为新的关键词/示例/门店规则 → 下一批自动识别
```

- 规则是 **YAML 可配**（类别关键词、尺寸区间、示例图、阈值），支持**门店级覆盖**。
- 示例池来自 `参考模板` 的 16 个原始文件 + 新标注样本，自动追加。
- 每批输出 `未知素材清单.csv`，一份"素材画像"（每店/每会员的 6 类数量、缺失、异常比例、未知比例）。

## 4. 预检模式（Dry-run）

只跑 ①–⑧ + 产出决策，**不渲染**，输出：能出哪几张 / 缺什么 / 需人工确认什么 / 识别准确率抽样 / API 成本预估。

这是 M2 的交付物：**先看报告，再花钱渲染**。

## 5. 性能与成本（本期不含视频）

| 动作 | 单张耗时 | 说明 |
| --- | --- | --- |
| 解包 + 嗅探 | <20 ms | 流式 |
| HEIC 解码 / 转码 | 150–400 ms | 多进程 |
| 质量评分（YOLO + 清晰度） | 80–150 ms | GPU 串行 |
| pHash 去重 | <10 ms | 内存 |
| 文档矫正（单应 / UVDoc） | 50 ms / 300 ms | 仅报告类 |
| VLM 分类 | 3–6 s/次（每次 4–6 张） | 3–5 并发 |

一个店（10 会员 ≈250 文件）：预处理 2–4 分钟，分类 3–5 分钟。

## 6. 预处理产出（`asset.json`）

```json
{
  "asset_id": "a_000123",
  "origin": {"batch": "b_...", "path": "宝安店/任胜男-candy/4333be...(1).jpg"},
  "hash": {"sha256": "…", "phash": "…"},
  "source_type": "image|live_photo|document|pdf|video_deferred|unknown",
  "normalized": {"file": "work/…/a_000123.jpg", "width": 4400, "height": 5500, "color": "sRGB"},
  "transform": {"rotate": 0, "rectify": "homography|uvdoc|none", "crop": [0, 0, 4400, 5500]},
  "quality": {"sharpness": 0.82, "exposure": 0.91, "subject_ratio": 0.34, "status": "ok|dropped|forced",
               "drop_reason": null},
  "dedup": {"duplicate_of": null},
  "class": {"kind": "body_scan", "view": "front", "phase": "both", "confidence": 0.94},
  "flags": ["already_masked", "contains_two_subjects"]
}
```

这份 JSON 是后续所有阶段的唯一输入——任何阶段都能只拿它重跑，不必碰原始 zip。
